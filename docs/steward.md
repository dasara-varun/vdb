# VDB Steward Specification

## Purpose

The Steward is VDB’s optional maintenance assistant. It makes the database easier to operate by explaining health signals and proposing bounded, reviewable changes. It is not the source of truth, not a superuser, and not a generic code executor.

## Initial implementation

The MVP uses deterministic diagnostics. The rules inspect health summaries, document counts, WAL size, schema samples, and query limits. A future local or private model may explain those findings, classify incidents, and answer user questions. The product remains useful without a model.

## Context boundary

The model receives the minimum context needed for a request: selected collection name, schema fingerprint, sampled types, query fingerprints, latency summaries, storage metrics, backup freshness, policies, and recent approved changes. Raw documents and secrets are excluded by default. Samples must pass field-level masking and size limits before entering model context.

## Modes

| Mode | Default | Behavior |
|---|---:|---|
| Observe | Yes | Read health metadata and produce findings only |
| Recommend | Later | Produce evidence-linked typed plans and wait for approval |
| Controlled Auto | Later | Execute only allowlisted reversible operations with budgets and verification |

## Typed finding contract

A finding includes an identifier, kind, severity, evidence, confidence, affected scope, recommendation, and approval requirement. It never contains an executable shell command or arbitrary query generated by the model.

## Action contract

A future action plan must contain the operation type, target instance and collection, preconditions, estimated cost, maximum budget, risk, approval requirement, expiration, expected postconditions, and rollback or recovery path. The policy engine validates this structure and rejects unknown operation types.

## Prompt injection defense

Documents, collection names, query text, and user-provided samples are untrusted data. They must be delimited and labeled as data before being supplied to a model. Instructions found inside data never modify the system policy. The model output is parsed as an untrusted value and cannot directly invoke the storage layer.

## Evaluation suite

Before enabling a new model or prompt, VDB should test schema-drift explanation, backup diagnosis, query-bound warnings, data redaction, unsafe-action refusal, malformed-plan rejection, prompt-injection resistance, evidence citation, and uncertainty behavior. The test set and model/prompt versions should be stored with the release record.

## Audit

Every model-assisted finding records the model identifier, prompt/template version, context hash, redaction policy version, output hash, parser result, policy decision, user approval, action result, and rollback reference. Logs must not contain raw secrets or unmasked sensitive values.
